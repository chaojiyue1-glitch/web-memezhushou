# Meme雷达产品设计规格书

版本：1.0  
日期：2026-09-04  
目标仓库：`chaojiyue1-glitch/web-memezhushou`  
项目形态：Windows 本地 Web 应用，个人使用

## 1. 项目定位

Meme雷达用于发现 Robinhood Chain 上刚创建或正在升温的低市值 Meme 币，并通过基础链上数据和指定 X KOL 的公开帖子提供早期线索。软件只做发现、筛选、解释和提醒，用户始终在外部平台手动交易。

产品不能宣称预测涨跌、保证收益或识别全部骗局。所有评分都是基于有限数据的筛选结果，不构成投资建议。

## 2. 目标用户与使用环境

- 单一用户，非商业 SaaS，不需要注册、登录、会员、权限或多租户系统。
- 用户不具备编程经验，安装、启动、停止和卸载必须能够通过双击 `.bat` 文件完成。
- 运行环境为 Windows 10/11。
- 软件仅在用户手动启动后台程序后工作。关机或停止软件时不扫描链上数据、不查询 X，也不补采停机期间的数据。

## 3. 核心目标

1. 尽早发现 Pons 和 Uniswap 上新出现的 Robinhood Chain Meme 交易池。
2. 通过简单、可解释的规则过滤明显不符合条件的币。
3. 把候选币分为“重点关注、普通观察、高风险”。
4. 对达到条件的币发送 Windows 系统通知。
5. 支持粘贴合约地址进行单币分析。
6. 监控用户指定的 X KOL，通过公开帖子发现低市值币。
7. 控制 X API 用量，并允许用户立即停止全部 X 请求。

## 4. 明确不做

- 不连接钱包，不读取或保存助记词、私钥及交易授权。
- 不自动买入、卖出、跟单或生成可签名交易。
- 不记录用户仓位、成本、盈亏和交易日记。
- 不使用 AI 判断买卖，不生成“建议买入”结论。
- 不提供复杂技术指标、量化策略、回测或价格预测。
- 不做 X 社交热度评分、复杂话题归类或每日简报。
- 不接入 Telegram、微信、邮件或手机 App。
- 不做云端运行、远程访问、多设备同步和用户账号。
- 第一版不接入 NOXA Fun、RamsesX 或其他公链。

## 5. 数据覆盖范围

### 5.1 链上范围

- 网络：Robinhood Chain Mainnet，Chain ID `4663`。
- Pons：监听官方活动合约的代币发行事件及相关交易池。
- Uniswap：监听 Robinhood Chain 上官方工厂合约创建的新交易池。
- 仅处理已经形成可交易池的代币；普通 ERC-20 部署不自动纳入扫描。
- 合约地址是代币的唯一身份。同名、同符号代币不得合并。

### 5.2 数据源策略

数据访问模块必须做成可替换适配器，不允许页面或评分逻辑直接依赖某一家 API。

- 实时链上事件：Robinhood Chain WebSocket/RPC。开发期可用官方公共 RPC；稳定运行可配置 Alchemy。
- Pons 元数据与事件：Pons 官方合约和公开集成文档。
- 交易池、价格与成交量：优先使用链上池事件或公开市场数据 API；若使用 GeckoTerminal/CoinGecko，必须遵守其限流并缓存结果。
- 合约、持仓与交易记录：Blockscout API 与链上 RPC。
- X 帖子与计数：X 官方 API，不使用网页爬虫。

所有生产合约地址必须由开发者在实现阶段从官方文档或官方浏览器再次核验，并放入集中配置文件。禁止把来源不明的合约地址散落在业务代码中。

## 6. 主要用户流程

1. 用户双击 `start.bat`。
2. 后台程序启动，本地网页自动在默认浏览器打开。
3. 扫描器从启动时刻开始监听 Pons 和 Uniswap；不追补停机历史。
4. 新交易池进入数据补充队列，软件收集基础交易、流动性、持仓和合约信息。
5. 至少积累 2 分钟数据后计算链上热度分与风险分；严重风险可以提前标记。
6. 达到“重点关注”条件时发送 Windows 通知，并写入机会列表。
7. 用户点击通知或列表项进入币种详情页。
8. 用户需要交易时点击外部交易页面链接，自行核对合约并手动操作。
9. 用户也可以粘贴 Robinhood Chain 合约地址，触发一次手动分析。
10. 若启用 X，后台每 5 分钟读取最多 10 位 KOL 的新增帖子；关闭软件或 X 总开关后立即停止。

## 7. 页面与功能

### 7.1 机会页

- 默认首页，优先展示最新“重点关注”币。
- 每行显示：币名、符号、合约缩写、来源、创建时间、热度分、风险等级、触发时间和主要触发原因。
- 显示后台扫描状态、最后更新时间和当日提醒数。
- 默认每日最多 20 条机会通知；数量可在设置中调整。若没有足够候选币，不补足数量。

### 7.2 全部新币页

- 展示最近 7 天扫描到的可交易币。
- 支持按重点关注、普通观察、高风险、Pons、Uniswap筛选。
- 支持按创建时间、热度分和风险分排序。
- 高风险币保留在列表中，但不发送机会通知。

### 7.3 手动分析页

- 接受一个 Robinhood Chain 合约地址。
- 校验地址格式、网络和是否存在交易池。
- 输出与自动扫描相同结构的基础报告。
- 查询失败时说明具体原因，不以 0 值冒充真实数据。

### 7.4 KOL监控页

- 最多保存 10 个 X 用户名。
- 支持添加、删除和单独暂停某位 KOL。
- 显示最近获取时间、最新帖子、识别到的币和匹配状态。
- 匹配状态分为：已由合约地址确认、名称/符号推测待确认、无法匹配。
- 只有已确认匹配且通过链上基础条件的低市值币才能发送 KOL 机会通知。

### 7.5 设置页

- 链上扫描状态与各数据源健康状态。
- X 数据采集总开关、单个 KOL 开关、Windows 通知开关、提示音开关。
- 最低流动性、热度提醒线、最高允许风险、每日提醒上限。
- X 月预算上限，默认 30 美元；显示本月本地估算用量。
- 数据清理按钮。
- API 配置状态只显示“已配置/未配置”，不得回显完整密钥。

### 7.6 币种详情页

- 身份：名称、符号、完整合约地址、来源、池地址、创建时间。
- 简单走势图：15 分钟、1 小时、6 小时、24 小时；显示价格和成交量。
- 市场数据：流动性、成交额、交易笔数、独立买家、买卖比例、估算市值或 FDV。
- 链上结论：热度分、风险分、每项通过或警告原因。
- X 信息：最近 24 小时提及数量、少量代表帖子、KOL 是否提及和原帖链接。
- 外部链接：官方区块浏览器和已确认的交易页面。
- 必须提示“卖出报价可获得不代表真实交易一定成功”和“评分不构成投资建议”。

## 8. 默认筛选与评分

默认值用于首轮实验，可在稳定性阶段根据真实样本调整。调整必须记录原因和前后效果。

### 8.1 基础门槛

- 代币年龄：至少 2 分钟，不超过 24 小时。
- 流动性：至少 10,000 美元。
- 最近 5 分钟交易数：至少 20 笔。
- 最近 5 分钟独立买家：至少 12 个。
- 可以从已知路由或报价器获得非零卖出报价。该检查仅代表可获得报价，不保证实际卖出成功。
- 没有触发严重风险条件。

### 8.2 链上热度分（0–100）

| 指标 | 权重 |
|---|---:|
| 成交量增长 | 25 |
| 独立买家增长 | 25 |
| 买入强度 | 15 |
| 流动性增长与稳定性 | 15 |
| 交易笔数增长 | 10 |
| 新币时效性 | 10 |

热度分达到 70 才能成为重点关注候选。

### 8.3 风险分（0–100，越高越危险）

| 指标 | 权重 |
|---|---:|
| 前十大非池子地址持仓集中度 | 25 |
| 创建者持仓及卖出行为 | 20 |
| 流动性水平及下降速度 | 20 |
| 基础合约权限与卖出报价 | 20 |
| 简单异常交易模式 | 15 |

简化版只检测可解释的基础异常，不实现复杂关联钱包图谱或机器学习刷量识别。

### 8.4 分类规则

- 重点关注：通过全部基础门槛，热度分不低于 70，风险分低于 50。
- 普通观察：未触发严重风险，但数据不足、热度不足或风险分在 50–69。
- 高风险：风险分不低于 70，或触发严重风险条件。

严重风险至少包括：无法获取必要池数据、流动性快速接近零、创建者短时大量卖出、检测到会阻止普通转出的明确合约限制。无法确认的检查必须标记“未知”，不能自动写成“安全”。

## 9. X与KOL规则

### 9.1 采集控制

- X 总开关关闭后，调度器必须停止 KOL 时间线、帖子搜索和帖子计数等全部 X API 请求。
- 关闭状态写入数据库，重启后保持关闭。
- 关闭时可以查看本地旧数据，但不能手动刷新 X。
- 再次开启后只从当前时间继续，不补查关闭或关机期间的数据。
- 单独关闭通知不等于停止采集，界面必须明确区分两个开关。

### 9.2 KOL扫描

- 最多 10 位，自定义添加，无预设推荐名单。
- 程序运行且 X 开启时，每 5 分钟检查一次新增帖子。
- 使用 `since_id` 或等效游标避免重复读取已处理帖子。
- 解析合约地址、`$符号`、币名和帖子链接。

### 9.3 平衡匹配

- 帖子包含合约地址且链上验证通过：已确认。
- 只有名称或符号：结合最近新币、创建时间、来源链接和链上池尝试匹配；必须显示“待确认”。
- 存在多个同名候选：不得自动选择。
- 待确认匹配不能触发强机会通知。

### 9.4 低市值定义

- 默认上限为估算市值 5,000,000 美元，可在配置文件中调整，首版不在普通设置页暴露。
- 若流通市值不可得，使用 FDV 并明确标为“FDV”，不得伪装成市值。
- 低市值只是一项发现条件，不表示低风险。

### 9.5 费用控制

- 用户设置的月预算上限默认为 30 美元。
- 达到本地估算额度的 80% 时显示警告。
- 达到本地估算额度的 100% 时暂停全部 X 请求，直到用户调整上限或进入下一个自然月。
- 本地费用根据请求类型、返回资源数及可配置单价估算。X 官方价格可能变化，因此页面必须说明“本地估算不等于官方账单”；官方开发者后台和预付额度才是最终账单依据。
- 单价配置必须集中管理，不得散落在代码中。

## 10. 通知规则

- 使用 Windows 系统通知，由后台程序发送，因此网页关闭时仍可通知。
- 后台程序停止后不得发送通知。
- 通知包含币名、来源、热度分、风险等级和一句触发原因。
- 点击通知打开本地详情页。
- 同一币首次达到重点关注时通知一次；只有分类发生明显改善或重新达到阈值且距上次至少 30 分钟，才允许再次通知。
- 默认每日机会通知上限 20 条；达到上限后继续记录机会但不弹窗。
- KOL 通知同样计入每日总上限，避免重复打扰。

## 11. 数据保存与清理

- 使用本地 SQLite。
- 原始池、价格、成交、持仓快照和普通新币保存 7 天。
- 触发过通知的币、评分结论和用户配置长期保留。
- 每日执行一次清理；用户可在设置页手动执行。
- 清理不得删除 API 配置、KOL名单和应用设置。
- 不上传本地数据库到 GitHub。

建议的逻辑实体：`tokens`、`pools`、`market_snapshots`、`holder_snapshots`、`scores`、`alerts`、`kol_accounts`、`x_posts`、`token_mentions`、`settings`、`api_usage`、`data_source_health`。

## 12. 技术结构

采用单机模块化结构：

- Python 后台：FastAPI 提供本地接口与网页服务，异步任务负责扫描和定时检查。
- 前端：服务端模板或轻量原生 JavaScript；不引入大型前端框架。
- 数据库：SQLite，加迁移机制。
- 链上访问：Web3.py 或等效成熟库。
- 图表：轻量图表库，仅实现本规格要求的价格与成交量。
- Windows 通知：使用维护中的 Windows Toast 兼容库，并提供通知失败降级。

内部模块边界：

1. `sources`：Pons、Uniswap、RPC、Blockscout、市场数据和 X 适配器。
2. `scanner`：实时事件、轮询、去重和任务队列。
3. `analysis`：指标计算、基础合约检查、热度与风险评分。
4. `matching`：KOL帖子解析和代币匹配。
5. `notifications`：限额、去重与 Windows 通知。
6. `storage`：数据库、迁移、保留和清理。
7. `web`：页面、只读展示、设置更新和健康状态。

任何一个外部数据源都不能直接控制通知；通知只能基于标准化数据和评分结果产生。

## 13. 安装、启动、停止与卸载

- `install.bat`：检查 Python、创建项目专用虚拟环境、安装依赖、创建 `.env`、初始化数据库并运行安装自检。若系统没有 Python，应给出清晰安装指引，不静默修改系统关键组件。
- `start.bat`：防止重复启动，启动后台服务，等待健康检查通过后打开默认浏览器。
- `stop.bat`：只停止本项目后台进程，不杀死其他 Python 进程。
- `uninstall.bat`：先停止本项目，明确列出删除范围并要求确认；删除虚拟环境、缓存、日志、数据库和本项目生成的快捷文件。不得自动卸载系统 Python。
- 用户若选择保留配置，卸载脚本应保留 `.env` 与设置导出；若选择完全删除，应提醒 `.env` 含 API 密钥。
- 停止或卸载 X 模块后，建议用户在 X 开发者后台撤销不用的密钥。

## 14. 异常处理

- RPC/WebSocket断开：指数退避重连，页面显示“扫描暂停”。
- 单个来源失败：隔离失败，其他来源继续工作。
- 数据不完整：显示“未知/数据不足”，不以 0 代替，不发送机会通知。
- API限流：遵守 `Retry-After`，降低频率，不进行高频重试。
- X失败或预算暂停：链上功能继续工作。
- Windows通知失败：记录错误，机会仍显示在网页。
- 数据库写入失败：停止生成新评分和通知，避免展示未保存的不一致状态。
- 所有日志应隐藏 API 密钥、完整授权头和其他敏感配置。

## 15. 测试与验收总原则

- 每个模块先写自动测试，再接入真实数据。
- 外部 API 测试使用固定样本和模拟响应，避免测试消耗 X 额度。
- 必须覆盖重复事件、断线重连、API限流、缺失字段、同名币、错误网络、数据库锁定和开关持久化。
- 必须有一项测试证明：X总开关关闭后，不会触发任何 X 网络请求。
- 必须有一项测试证明：`stop.bat` 只停止本项目进程。
- 必须有一项测试证明：API密钥不会出现在日志、网页和 Git 提交中。
- 真实链上试运行至少观察 24 小时，再决定默认阈值是否需要校准。
- 每个阶段完成后 Codex 必须暂停，报告完成内容、测试结果、已知限制和用户验证步骤，等待用户明确批准后进入下一阶段。

## 16. 开发阶段

### 阶段1：链上可用版

完成项目骨架、数据库、Pons与Uniswap扫描、数据标准化、基础评分、机会页、全部新币页、手动分析、详情页、走势图、Windows通知、设置、7天清理和四个 Windows 脚本。

### 阶段2：X与KOL

完成 X 总开关、最多10位KOL、5分钟增量检查、平衡匹配、低市值过滤、详情页24小时提及量与代表帖子、费用估算和30美元默认上限。

### 阶段3：测试与校准

完成真实运行观察、阈值校准、断线与限流验证、性能检查、文档补齐和最终用户验收。第一版结束时仍不扩展其他平台、公链或云端部署。

预计从开始开发到可稳定试用为 7–14 天，具体取决于外部 API 开通、Robinhood Chain 数据完整性和真实运行中发现的问题。该估计不是交付承诺。

## 17. 成功标准

项目完成时，非技术用户能够：

1. 按说明完成安装并双击启动。
2. 看见后台是否正在扫描以及数据是否正常更新。
3. 在机会页收到经过基础筛选的币种提示。
4. 打开详情页理解触发原因和主要风险。
5. 粘贴一个有效合约得到基础分析，错误输入得到清楚提示。
6. 添加、暂停和删除 KOL。
7. 一键暂停全部 X 数据采集，并确认不再消耗 API。
8. 安全停止或卸载应用，不影响电脑上的其他程序。

## 18. 安全与免责声明

- 软件只提供信息整理和风险筛选，不提供投资建议。
- Meme币可能剧烈波动、流动性消失或归零。
- 任何“低风险”只表示在当前有限检查中未发现指定异常，不表示安全。
- 用户交易前必须再次核对完整合约地址、池深度、滑点和钱包交易预览。
- 项目仓库必须为私有仓库；`.env`、数据库、日志、缓存和 API 密钥必须加入 `.gitignore`。
